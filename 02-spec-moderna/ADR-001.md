# ADR-001: Arquitetura — Modular Monolith em vez de Microsserviços

![ESTÁGIO 02 Spec](https://img.shields.io/badge/ESTÁGIO-02%20Spec-00A4EF?style=for-the-badge) ![STATUS Aceita](https://img.shields.io/badge/STATUS-Aceita-7FBA00?style=for-the-badge)

**Data:** 27/05/2026
**Status:** Aceita
**Decisores:** Par 2 (Enterprise Architect + Software Architect) com revisão do Par 1 (Product Owner)

---

## Contexto

O SIFAP legado é um monolito Natural/Adabas com 15 programas que operam sobre 4 DDMs compartilhados. A equipe precisa decidir a arquitetura-alvo para o SIFAP 2.0 antes de iniciar o Estágio 3.

A pressão natural em projetos de modernização é "já que estamos reescrevendo, vamos para microsserviços". As restrições reais do projeto são:

- **Time de 5 pessoas** com prazo de 1 dia de workshop
- **18 regras de negócio críticas** dispersas entre módulos que se comunicam via dados compartilhados
- **Zero operação distribuída** atual — nenhuma experiência de equipe com service mesh, observabilidade distribuída ou eventual consistency
- **Dados altamente acoplados**: `PAGAMENTO` depende de `BENEFICIARIO` e `PROGRAMA-SOCIAL` para calcular qualquer valor
- **Auditoria transacional**: toda alteração deve ser auditável em mesma transação ACID

---

## Opções Consideradas

### Opção 1: Modular Monolith (uma unidade implantável, módulos internos separados)

- **Descrição**: Único JAR Spring Boot com pacotes internos organizados por bounded context (`beneficiary`, `payment`, `eligibility`, `program`, `audit`). Comunicação entre módulos via interfaces Java (sem chamadas de rede). Único banco PostgreSQL.
- **Vantagens**:
  - Transações ACID entre módulos sem saga ou compensação
  - Deploy, monitoramento e debugging simples
  - Time de 5 pessoas consegue entregar em 1 dia
  - Fronteiras de módulo podem ser endurecidas para microsserviços futuros se necessário (Strangler Fig)
  - Menor complexidade operacional: sem service discovery, sem circuit breaker, sem distributed tracing obrigatório
- **Desvantagens**:
  - Módulos podem se acoplar indevidamente se disciplina de código não for mantida
  - Escala horizontal afeta todos os módulos juntos

### Opção 2: Microsserviços desde o início

- **Descrição**: Serviços separados para `beneficiary-service`, `payment-service`, `eligibility-service`, cada um com seu banco.
- **Vantagens**:
  - Escala independente por serviço
  - Times independentes por serviço
- **Desvantagens**:
  - Cálculo de pagamento exige dados de 3 agregados → chamadas síncronas ou eventos assíncronos
  - Auditoria transacional impossível sem saga pattern (complexidade exponencial)
  - 5 pessoas não conseguem operar 5+ serviços em 1 dia
  - Nenhuma das 18 BRs exige escala independente por domínio

### Opção 3: Modular Monolith com módulos como bibliotecas Maven separadas

- **Descrição**: Cada módulo é um artefato Maven (`sifap-beneficiary`, `sifap-payment`, etc.) dentro de um multi-module project. Deployment continua único.
- **Vantagens**: Fronteiras de compilação entre módulos (dependências explícitas no pom.xml)
- **Desvantagens**: Overhead de build, complexidade de versionamento sem benefício real no prazo dado

---

## Decisão

**Decidimos usar Modular Monolith (Opção 1): um único JAR Spring Boot 3.3 com módulos internos organizados por bounded context, usando package-by-feature.**

---

## Justificativa

A Opção 1 atende todos os requisitos do domínio (ACID, auditoria, cálculos transversais) com a menor complexidade operacional possível para um time de 5 pessoas. As 18 BRs identificadas no Estágio 1 mostram alto acoplamento de dados entre `BENEFICIARIO`, `PAGAMENTO` e `PROGRAMA-SOCIAL` — justamente o cenário onde microsserviços introduzem mais problemas do que resolvem.

A Opção 3 foi descartada por complexidade de build sem benefício de runtime no prazo dado.

As fronteiras internas dos módulos são desenhadas de forma que uma futura extração para microsserviços (Strangler Fig) seja viável, caso o sistema cresça além do que um monolito suporta.

---

## Consequências

### Positivas

- Deploy e operação simples: um processo, um banco, um conjunto de logs
- Transações ACID cobrindo múltiplos módulos em uma única operação (essencial para REQ-AUD-003)
- Time consegue entregar no prazo do workshop
- Debugging local sem necessidade de orquestração de múltiplos serviços

### Negativas

- Módulos internos podem se acoplar se as interfaces não forem respeitadas — mitigação: `ArchUnit` no CI verificando que nenhum módulo importa classes internas de outro
- Escala horizontal do monolito: se `payment-batch` escalar diferente de `beneficiary`, precisará de extração futura — mitigação: Spring Batch já suporta particionamento

### Riscos

- Risco: equipe do Estágio 3 ignora fronteiras de módulo por conveniência
- Mitigação: instrução no `modular-monolith.instructions.md` + ArchUnit test que falha o build ao detectar violação de fronteira
