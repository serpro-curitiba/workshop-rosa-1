# ADR-003: Autenticação e Autorização — OAuth2/JWT via Gov.br

![ESTÁGIO 02 Spec](https://img.shields.io/badge/ESTÁGIO-02%20Spec-00A4EF?style=for-the-badge) ![STATUS Aceita](https://img.shields.io/badge/STATUS-Aceita-7FBA00?style=for-the-badge)

**Data:** 27/05/2026
**Status:** Aceita
**Decisores:** Par 2 (Software Architect) + Par 4 (QA Engineer) + Par 5 (DevOps)

---

## Contexto

O SIFAP legado não tem autenticação federada: usuários são validados por controle interno do Natural. O SIFAP 2.0 precisa de:

1. **Autenticação**: quem é o usuário (identidade governamental)
2. **Autorização**: o que o usuário pode fazer (perfis: OPERATOR, AUDITOR, MANAGER, ADMIN)
3. **Auditabilidade**: todo acesso rastreável ao usuário responsável (exigência de REQ-AUD-003)
4. **Conformidade**: LGPD exige controle de acesso a dados de PII (CPF, renda, composição familiar)

O descoberta report §2.3 identificou 4 perfis de usuário. A equipe precisa decidir o mecanismo de autenticação antes de projetar os endpoints da API.

---

## Opções Consideradas

### Opção 1: OAuth2/JWT via Gov.br (SSO do Governo Federal)

- **Descrição**: Spring Security configurado como Resource Server OAuth2. Frontend Next.js usa PKCE flow com Gov.br como Authorization Server. Tokens JWT carregam claims de perfil. Gov.br é o IdP oficial do Governo Federal Brasileiro.
- **Vantagens**:
  - SSO unificado com outras aplicações governamentais
  - Identidade verificada pelo próprio governo (SERPRO/Gov.br)
  - Sem gerenciamento de senhas locais
  - Conformidade com padrões de segurança governamentais (e-MAG, ETDA)
  - Claims de CPF e nome já presentes no token Gov.br
- **Desvantagens**:
  - Dependência de disponibilidade do Gov.br
  - Configuração de OIDC discovery pode variar entre ambientes

### Opção 2: Keycloak self-hosted como IdP interno

- **Descrição**: Keycloak rodando em container gerenciado pela própria equipe. Spring Security como Resource Server.
- **Vantagens**: Controle total do IdP, sem dependência de serviço externo
- **Desvantagens**:
  - Infraestrutura adicional para operar (mais um serviço para o Par 5)
  - Integração com Gov.br ainda necessária para identificação governamental
  - Duplicação de responsabilidade: já existe IdP governamental disponível

### Opção 3: Autenticação local (usuário/senha no banco)

- **Descrição**: Tabela de usuários no PostgreSQL, Spring Security com BCrypt
- **Vantagens**: Zero dependência externa
- **Desvantagens**:
  - Gerenciamento de senhas expõe risco OWASP A07 (falhas de identificação)
  - Sem SSO: usuário precisa de credencial separada para cada sistema governamental
  - Não é padrão para aplicações do Governo Federal

---

## Decisão

**Decidimos usar OAuth2/JWT via Gov.br (Opção 1) como mecanismo de autenticação. Perfis de autorização são gerenciados localmente no SIFAP 2.0 via roles mapeadas a partir de claims do token.**

---

## Justificativa

Gov.br é o padrão de autenticação para aplicações do Governo Federal. A identidade governamental do usuário está disponível diretamente no token, eliminando a necessidade de gestão de credenciais. Spring Security 6 (incluído no Spring Boot 3.3) tem suporte nativo a OAuth2 Resource Server com validação de JWT. O frontend Next.js 15 implementa o PKCE flow via `next-auth` ou bibliotecas equivalentes sem expor secrets no client.

Autorização por perfil é gerenciada localmente: o SIFAP 2.0 mantém uma tabela de mapeamento `user_profile(gov_br_cpf, profile)` que o administrador gerencia. O token Gov.br prova a identidade; a tabela local define o que o usuário pode fazer no SIFAP.

---

## Consequências

### Positivas

- Zero gestão de senhas no SIFAP 2.0
- CPF do usuário disponível no token → rastreabilidade de auditoria automática (REQ-AUD-003)
- SSO com outras aplicações governamentais
- Conformidade com normas de segurança do Governo Federal

### Negativas

- Dependência de disponibilidade do Gov.br em ambiente de produção — mitigação: circuit breaker com fallback para token em cache (TTL curto)
- Ambiente de desenvolvimento precisa de mock do Gov.br — mitigação: Keycloak local em `docker-compose.yml` simulando o endpoint OIDC

### Riscos

- Risco: claims do token Gov.br mudarem de formato sem aviso
- Mitigação: `UserInfoMapper` isolado com teste de contrato; alerta de monitoramento em falha de parsing

## Perfis de Autorização

| Perfil | Operações permitidas |
|--------|----------------------|
| OPERATOR | Cadastro de beneficiários, aprovação de pagamentos PENDING |
| AUDITOR | Leitura de trilha de auditoria, exportação de relatórios |
| MANAGER | Visualização de relatórios financeiros e ciclos |
| ADMIN | Tudo + gestão de usuários, perfis e prefixos CPF especiais |
