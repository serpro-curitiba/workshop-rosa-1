# ADR-004: Dicionário Canônico de Status de Pagamento (resolve MYS-010)

![ESTÁGIO 02 Spec](https://img.shields.io/badge/ESTÁGIO-02%20Spec-00A4EF?style=for-the-badge) ![STATUS Aceita](https://img.shields.io/badge/STATUS-Aceita-7FBA00?style=for-the-badge)

**Data:** 27/05/2026
**Status:** Aceita
**Decisores:** Par 2 (Software Architect) + Par 4 (DBA) com revisão do Par 1 (Requirements Engineer)

---

## Contexto

O Estágio 1 identificou **MYS-010**: o DDM `PAGAMENTO.ddm` usa o valor `X` para o status "Cancelado", enquanto os programas de relatório Natural (`RELPGT.NSN`, `BATCHREL.NSN`) usam o valor `C` para o mesmo conceito. Essa inconsistência existe há anos no legado e foi mantida por inércia — nenhum programa atual faz a conversão explicitamente.

No SIFAP 2.0, uma única string de status percorre o banco de dados, a API REST, o frontend e os relatórios. Se não decidirmos o dicionário canônico agora, cada módulo do Estágio 3 inventará sua própria convenção, reproduzindo o problema do legado em Java.

Além da inconsistência `X/C`, o legado não tem representação para os estados intermediários modernos (`PENDING`, `APPROVED`, `REJECTED`, `RECONCILED`, `DIVERGENT`) — eles estavam implícitos no fluxo de programas Natural.

---

## Opções Consideradas

### Opção 1: Manter os valores do DDM (X, C, A, S, P conforme PAGAMENTO.ddm)

- **Descrição**: Usar os valores originais do Adabas como strings na API moderna
- **Vantagens**: Zero mapeamento durante migração de dados históricos
- **Desvantagens**:
  - `X` é ambíguo (parece um placeholder)
  - Inconsistência com `C` dos relatórios reproduzida no moderno
  - Strings de 1 caractere são incompreensíveis em logs e APIs REST

### Opção 2: Dicionário canônico em inglês (PENDING, APPROVED, REJECTED, RECONCILED, DIVERGENT, CANCELLED)

- **Descrição**: Enum Java `PaymentStatus` com 6 valores em inglês, usados em toda a codebase. Mapeamento explícito legado→moderno na migração de dados e no relatório de conciliação.
- **Vantagens**:
  - Sem ambiguidade: nomes autodocumentados
  - Cobre todos os estados do fluxo moderno (ciclo completo PENDING→APPROVED→RECONCILED)
  - Internacionalizável para relatórios em inglês e português
  - Tabela de mapeamento documentada e testável
- **Desvantagens**:
  - Migração de dados históricos requer script de conversão (gerenciável)

### Opção 3: Dicionário em português (PENDENTE, APROVADO, REJEITADO, CONCILIADO, DIVERGENTE, CANCELADO)

- **Descrição**: Enum Java em português
- **Vantagens**: Legível por usuários brasileiros sem tradução
- **Desvantagens**:
  - Convenção do projeto é Java em inglês (copilot-instructions.md)
  - Conflito com padrão de nomenclatura do Estágio 3

---

## Decisão

**Decidimos usar o dicionário canônico em inglês (Opção 2):**

```
PENDING     → Pagamento gerado, aguardando aprovação
APPROVED    → Aprovado por OPERATOR ou ADMIN
REJECTED    → Rejeitado por OPERATOR ou ADMIN
RECONCILED  → Conciliação bancária confirmada (diferença ≤ R$ 0,01)
DIVERGENT   → Conciliação bancária com divergência (diferença > R$ 0,01)
CANCELLED   → Cancelado após aprovação
```

**Mapeamento legado → SIFAP 2.0:**

| Valor DDM/Relatório legado | SIFAP 2.0 |
|---|---|
| `X` (PAGAMENTO.ddm) | `CANCELLED` |
| `C` (relatórios Natural) | `CANCELLED` |
| `A` (ativo/processado) | `APPROVED` |
| `P` (pendente, inferido) | `PENDING` |
| `D` (divergência, inferido) | `DIVERGENT` |
| Sem equivalente | `RECONCILED`, `REJECTED` |

---

## Justificativa

A Opção 2 elimina a ambiguidade MYS-010 de forma definitiva e segue a convenção Java em inglês do projeto. O custo (script de migração) é pequeno e executado uma única vez. O REQ-STATUS-001 em SPECIFICATION.md formaliza o dicionário como requisito verificável no CI.

---

## Consequências

### Positivas

- MYS-010 resolvido definitivamente: zero ocorrência de `X` ou `C` na codebase moderna
- Status autodocumentado em logs, APIs e relatórios
- Enum Java `PaymentStatus` compilado: nenhuma string mágica de status na codebase
- API OpenAPI documenta automaticamente os 6 valores possíveis

### Negativas

- Script de migração de dados históricos necessário — mitigação: migration Flyway `V2__migrate_payment_status.sql` com mapeamento explícito e rollback
- Relatórios regulatórios (TCU) ainda usam terminologia em português — mitigação: camada de tradução no serviço de relatório, não no modelo de domínio

### Riscos

- Risco: valores `X` ou `C` infiltrarem via integração de dados do legado durante coexistência (ADR-002)
- Mitigação: anti-corruption layer no adapter de importação batch valida e converte antes de persistir
