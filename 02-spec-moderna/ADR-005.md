# ADR-005: Constante 0.347215 (Fator K) como Parâmetro Externalizável (resolve MYS-001)

![ESTÁGIO 02 Spec](https://img.shields.io/badge/ESTÁGIO-02%20Spec-00A4EF?style=for-the-badge) ![STATUS Aceita](https://img.shields.io/badge/STATUS-Aceita-7FBA00?style=for-the-badge)

**Data:** 27/05/2026
**Status:** Aceita
**Decisores:** Par 2 (Enterprise Architect + Software Architect) com revisão do Par 3 (Technical Lead)

---

## Contexto

O Estágio 1 identificou **MYS-001**: o programa `CADPROG.NSN` linhas 87-88 multiplica o fator de reajuste pela constante `0.347215` sem nenhuma documentação, comentário ou referência normativa. A hipótese do time é que se trata de uma calibração histórica para compatibilizar o legado com um lote antigo.

Essa constante afeta **o valor base de todos os programas sociais cadastrados** e, por cascata, o cálculo de **todos os benefícios mensais** (BR-004 → BR-005). Uma migração que altere ou ignore este valor produzirá divergência financeira em toda a base de pagamentos.

A equipe precisa decidir: mantém a constante hardcoded no código Java, ou a externaliza como parâmetro configurável?

---

## Opções Consideradas

### Opção 1: Hardcode da constante como literal numérico em Java

- **Descrição**: `static final BigDecimal FATOR_K = new BigDecimal("0.347215");` no código
- **Vantagens**: Simples, sem configuração
- **Desvantagens**:
  - Valor mágico migrado do legado sem explicação no código moderno
  - Mudança futura (ex.: descoberta da origem normativa) exige redeployment
  - Impossível auditar alterações sem recompilação

### Opção 2: Constante nomeada em `application.properties` / variável de ambiente

- **Descrição**: `sifap.payment.fator-k=0.347215` no `application.properties`, injetado via `@Value`. Pode ser sobrescrito por variável de ambiente `SIFAP_FATOR_K` sem redeployment.
- **Vantagens**:
  - Valor mágico documentado com nome semântico (`sifap.payment.fator-k`)
  - Alterável sem recompilação (útil se origem normativa for descoberta)
  - Alteração via variável de ambiente auditável via ConfigMap/Secret do Kubernetes
- **Desvantagens**:
  - Configuração incorreta pode afetar todos os cálculos — mitigação: validação de range no startup

### Opção 3: Parâmetro armazenado no banco de dados (tabela `system_config`)

- **Descrição**: Tabela `system_config(key, value)` com registro `fator_k=0.347215`. Atualizável via endpoint de administração.
- **Vantagens**: Alterável em runtime sem restart
- **Desvantagens**:
  - Complexidade desnecessária para um parâmetro que raramente muda
  - Alteração em runtime de parâmetro financeiro sem janela de manutenção é risco de compliance

---

## Decisão

**Decidimos externalizar o FATOR_K como propriedade de configuração (Opção 2), com:**

- Valor padrão `0.347215` no `application.properties` (idêntico ao legado)
- Sobrescrita via variável de ambiente `SIFAP_FATOR_K` em cada ambiente
- Validação no startup: se `FATOR_K <= 0` ou `FATOR_K > 1`, a aplicação recusa inicializar
- Toda alteração de `FATOR_K` grava evento de auditoria (REQ-PROG-001)

---

## Justificativa

A Opção 2 resolve MYS-001 sem over-engineering: o valor mágico ganha nome semântico, fica documentado no código, e pode ser corrigido sem redeployment se a equipe de negócio descobrir a origem normativa. A Opção 3 foi descartada — alterar um parâmetro financeiro crítico em runtime sem janela de manutenção é risco de compliance para um sistema de pagamentos governamentais.

O valor `0.347215` é mantido idêntico ao legado como padrão. Qualquer desvio requer decisão consciente do administrador, rastreada em auditoria.

---

## Consequências

### Positivas

- MYS-001 documentado: o código agora tem um nome semântico (`fator-k`) em vez de um literal opaco
- Possível correção futura sem recompilação
- Testes de equivalência legado vs. moderno passam com `FATOR_K=0.347215`
- Alteração em produção requer mudança de variável de ambiente → rastreável em pipeline de IaC

### Negativas

- Risco de configuração incorreta em ambiente de homologação usando valor diferente do produção — mitigação: pipeline de CI valida que `SIFAP_FATOR_K` tem o mesmo valor em HML e PROD ou levanta alerta

### Riscos

- Risco: origem normativa descoberta exige mudança retroativa em pagamentos históricos
- Mitigação: REQ-PAY-003 (correção retroativa com guard) cobre o cenário de reprocessamento retroativo

---

## Nota Histórica

O nome `FATOR-K` é o campo do DDM `PROGRAMA-SOCIAL`. O `K` provavelmente é uma referência a "konstante" (convenção alemã para constantes em sistemas financeiros legados dos anos 90), mas não há confirmação documental. A hipótese de calibração para compatibilidade com lote antigo (anterior a 1997) permanece como mais provável pelo time de arqueologia.
